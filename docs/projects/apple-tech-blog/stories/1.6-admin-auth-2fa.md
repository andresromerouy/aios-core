# Story 1.6: Autenticación admin con 2FA TOTP obligatorio

## Status

Draft

## Story

**As a** dueño-administrador,
**I want** loguearme al panel admin con email + contraseña + un segundo factor TOTP obligatorio,
**so that** mi acceso al CMS está protegido aunque alguien obtenga mi contraseña.

## Acceptance Criteria

1. El usuario admin inicial puede loguearse en `/admin` con email + contraseña.
2. En el primer login, el sistema obliga a enrolar un dispositivo TOTP (Google Authenticator, 1Password, Authy) mostrando un QR.
3. Logins subsecuentes piden el código TOTP de 6 dígitos tras pasar email + password.
4. Códigos de respaldo (backup codes) generados al enrolar y mostrados una sola vez para guardar.
5. Posibilidad de regenerar backup codes desde el perfil del usuario.
6. Rate-limiting en login (máx 5 intentos fallidos por IP / 15 min) implementado vía Upstash Redis.
7. Sesiones expiran tras 12h de inactividad (configurable).
8. Login exitoso, login fallido y enrolamiento TOTP generan entradas en `AuditLogs` (collection se crea en Story 6.2 inicialmente, pero el `writeAuditLog()` helper puede crearse acá con stub).

## Story Points

**5 pts** (complejo, 3-6h focused).

**Split fallback:** si supera 4h, partir en `1.6a Auth básica + rate-limit` y `1.6b TOTP + backup codes`.

## Dev Notes

### Architecture §7.5 — Auth flow sequence

Ver Architecture §7.5 diagrama. Resumen:

1. POST `/admin/login` con email + password → si OK + `totpEnabled=true`, retornar ticket pre-auth.
2. POST `/api/admin/2fa/verify` con ticket + code → si OK, crear sesión + setear cookie.

### Storage del TOTP secret

- **Encriptar at-rest:** el `totpSecret` no debe persistirse en plano. Opciones:
  - Encriptar con `PAYLOAD_SECRET` como key (AES-256-GCM) antes de persistir. Helper `src/lib/crypto.ts`.
  - Decisión simple: Payload por default cifra ciertos fields si se marca `admin: { hidden: true }` (sigue siendo plaintext en DB). **Implementar cifrado explícito** vale la pena.
- Backup codes: hashear con bcrypt al persistir (como passwords); comparar al verificar.

### Riesgos asociados

- **Lockout accidental del dueño:** si pierde el dispositivo TOTP y todos los backup codes. Mitigación: imprimir o foto-respaldar los 10 backup codes al enrolar. **Documentar este flujo en el runbook (Story 6.6).**
- **Tiempo del servidor desalineado:** TOTP depende de clock sync. Vercel sirve en UTC ajustado por NTP, mínimo riesgo.

### Testing

Cuando Vitest esté disponible (Story 1.9), test files en `tests/unit/lib/totp.test.ts` y `tests/unit/lib/rate-limit.test.ts`.

E2E completo del flujo (login + 2FA) → diferido a Story 6.7 (E2E suite).
