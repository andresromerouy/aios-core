# Story 1.5: Deploy automático en Vercel con preview por PR

## Status

Draft

## Story

**As a** dueño-dev,
**I want** que cada PR genere un preview deploy en Vercel automáticamente y que `main` deploye a producción,
**so that** puedo validar cambios visualmente antes de mergear y publicar en producción sin esfuerzo manual.

## Acceptance Criteria

1. Proyecto conectado a Vercel via GitHub integration (no manual CLI deploys).
2. Variables de entorno configuradas en Vercel para los entornos preview + production: `DATABASE_URL`, `PAYLOAD_SECRET`, `PAYLOAD_PUBLIC_SERVER_URL`, `CRON_SECRET`.
3. Cada PR genera un preview URL `*.vercel.app` accesible y comentado en el PR por el bot de Vercel.
4. Merge a `main` triggerea deploy a producción automáticamente.
5. URL de producción `*.vercel.app` accesible públicamente con HTTPS forzado (Vercel default).
6. Documentado en README cómo añadir nuevas environment vars en Vercel.
7. **Neon-Vercel integration activa**: cada PR crea automáticamente un branch de DB Neon para el preview, evitando contaminar `main` DB.
8. **Vercel Cron Jobs verificado**: confirmar plan Vercel (Hobby permite hasta 2 crons; Pro permite ilimitados) — si llegamos a necesitar los 4 crons del Architecture §9.2 en Hobby, evaluar consolidar.

## Dev Notes

```json
{
  "crons": [
    { "path": "/api/cron/publish-scheduled", "schedule": "*/5 * * * *" },
    { "path": "/api/cron/send-scheduled-newsletters", "schedule": "*/5 * * * *" }
  ]
}
```

Los cleanup crons se agregan más adelante (Story 6.2 / 6.5). Sin endpoints implementados todavía, Vercel logueará error 404 — está bien.

### Connection pooling con Neon

Para evitar saturar la DB desde Vercel serverless functions:
- Usar `DATABASE_URL` con `-pooler.<region>.aws.neon.tech` (pgbouncer).
- En `payload.config.ts`, configurar `pool: { max: 10 }` (default conservador).

### Riesgos asociados

**R4 (Architecture §19) — Vercel Cron en Hobby tiene límite de 2 crons.** Mitigación aplicada en Task 6: consolidar cleanup crons en un dispatcher.
